Rules
Patches live in patches/ and are applied in file-name order by scripts/patches.sh with git apply. vscode/ is fetched at the pinned tag and never hand-edited; every change to it is a patch, one concern per patch. Order matters: scripts/patches.sh runs with set -euo pipefail, so it stops at the first patch that fails to apply, the build workflow fails and the pull request's CI is red. A red pull request is not merged.

Product settings: product.overrides.json

Brand names, ids, links, the gallery and the default theme are one JSON file, not patches. scripts/assets.sh merges it into the upstream product.json with jq after the patches are applied.

Step in scripts/assets.shWhat it does
1jq -s reads vscode/product.json and product.overrides.json; the overrides are merged over upstream with * (objects merge, overrides win).
2removeKeys is dropped from the merged object, then each listed key is deleted with delpaths.
3defaultChatAgent is kept, but every string value that starts with http:// or https:// is set to "".
4The result is written to product.json.new and moved over vscode/product.json.
Why defaultChatAgent is kept, not removed
Upstream reads defaultChatAgent unguarded in more than 60 places, so deleting the key would crash those readers. It stays in product.json with every http(s) URL blanked, so the built-in chat has nothing to call. Together with patch 0005 (chat.disableAIFeatures true) the chat stays inert.
Residual risk
If chat is ever re-enabled, chatEntitlementService's free sign-up path calls request('') with the blanked URL. That is an empty-URL request, not a call to Microsoft, but it is a failure path nobody has exercised. Not tested; re-check it before any change that turns chat back on.

How a patch is made and updated (T05)

The repo has scripts/save_patch.sh. It writes a patch from the working tree of vscode/; there is no other tool.

StepHow a patch is made or updated today (T05)
1scripts/prepare_vscode.sh gives a clean vscode/ at the pinned tag (checkout -f, clean -fdq) and fails if HEAD is not the commit in upstream.json.
2To change patch N: apply the patches before it (scripts/patches.sh applies all of them in file order, so for a middle patch apply them by hand with git -C vscode apply), and stage that state with git -C vscode add -A so the index is the base.
3Edit the files in vscode/ for that one concern.
4Run scripts/save_patch.sh patches/NNNN-name.patch. It keeps the header of the existing patch (every line up to the first blank line: Subject and the source line) and writes git -C vscode diff after it, to a .new file that replaces the patch. A new patch has no header to keep: write Subject and the source line ("Original to OmnIDE" or "Adapted from VSCodium (MIT), patches/..., Copyright (c) VSCodium contributors, MIT") into the file first.
5Run scripts/patches.sh on a fresh prepare_vscode.sh checkout: every patch must apply in order. CI does the same on every pull request.
6After an upstream bump (Renovate edits upstream.json): if a patch no longer applies the build fails; repeat steps 1 to 4 for that patch against the new tag. The bump is not merged red.

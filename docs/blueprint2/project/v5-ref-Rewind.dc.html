Rewind limits and warnings

What a checkpoint restore can and cannot bring back. The limits below are Claude Code's file checkpointing; where OmnIDE keeps its own turn checkpoints is in the Storage card.

CaseWhat happens
Rewind menu actionsRestore code and conversation; Restore conversation; Restore code; Summarize from here (compress the conversation from that point forward into a summary, freeing context); Summarize up to here (compress the conversation before that point, later messages kept); Never mind. The two code options show only when the checkpoint has tracked file changes. Summarize leaves files alone and the original messages stay in the session transcript.
Checkpoints keptFile snapshots are kept for the 100 most recent checkpoints in a session; discarding an older one deletes snapshot files no remaining checkpoint uses, except each file's first snapshot.
Open the menu/rewind (alias /undo), or Esc twice when the prompt is empty. Every prompt that starts a turn creates a checkpoint, saved with the conversation, so /rewind still works after resume
Files changed only by BashNot captured. Once an edit tool has touched a file, later Bash changes to that file are undone too
Messages sent while Claude is workingMay show "No code restore": no checkpoint of their own. Rewind to the prompt that started the turn to undo that turn's edits
Edits by most subagents, or by another session or outside toolNot captured. A foreground forked skill edits during your own turn, so it is restored; a background one (the default) is not
Symlinked and hard-linked filesSkipped, with the warning "Restored the code, but skipped N files"
About 30 days after the session last saved a snapshotThe retention sweep deletes the session's snapshots (keep them longer with cleanupPeriodDays); rewind can fail with "No files were restored"

Storage: Agent Host checkpoints (git refs)
The Agent Host service agentHostCheckpointService.ts writes one git ref per turn into the workspace repo: refs/agents/<sessionId>/checkpoints/turn/<N> (peer chats: refs/agents/chats/<chatKey>/checkpoints/turn/<N>, chatKey = first 16 hex of the SHA-1 of the stored URI). Each ref is a commit of a tree captured through a temporary index: a baseline at turn/0, then a capture at turn start and one at turn end. A turn that changes nothing reuses the parent ref. The baseline is captured when the session materialises (the first send) and is best effort: if the capture fails, a warning is logged ("Baseline checkpoint capture failed") and the session carries on. See session, turn and cancel for what Restore Checkpoint does with these refs.
Where they live and how they are used
Inside <repo>/.git/refs/, so they survive restarts, never show as branches or tags, and are separate from the chat extension's refs/sessions/.... A folder that is not a git repo is skipped. Refs are deleted when the session's data is deleted. The per-turn changes view reads the pair of refs for a turn (so terminal edits show up too).
Not verified
The SDK is also started with enableFileCheckpointing: true (claudeSdkOptions.ts:186), but no production call to rewindFiles was found, so which mechanism a restore uses is not confirmed. There is no shadow git repo and no checkpoints.ts in the extension.
